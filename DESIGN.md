# Dodo Payments — Design Document

## 1) Data Model

The service uses PostgreSQL with UUID primary keys for all externally visible resources.

Reason for UUIDs: they are globally unique, safe for distributed writes, and do not leak sequence volume in URLs.

### Tables and purpose

- `businesses`: tenant root.
- `api_keys`: hashed API keys (`key_hash`) linked to one business, with `revoked_at` for revocation.
- `customers`: customer identity per business (`UNIQUE (business_id, email)`).
- `invoices`: state machine owner; stores `state`, `total_cents`, due date and description.
- `invoice_line_items`: immutable line-level monetary inputs; `line_total_cents` is generated by DB.
- `payment_attempts`: idempotency + payment lifecycle (`pending/succeeded/failed`) and PSP metadata.
- `webhook_endpoints`: destination URLs and signing secret per business.
- `webhook_deliveries`: delivery queue with retry metadata (`status`, `attempt_count`, `next_retry_at`).

### Index strategy

- `api_keys(key_hash)` for auth lookup.
- `customers(business_id)` and unique email composite.
- `invoices(business_id, state)` for filtered list endpoints.
- `payment_attempts(idempotency_key)` for retry-safe payment behavior.
- partial index on `webhook_deliveries(status, next_retry_at)` where status needs work.

### Scaling notes (100x)

- Partition `invoices` and `payment_attempts` by `business_id` or time.
- Add read replicas for list-heavy reads.
- Add dedicated queue system (e.g., Redis/SQS/Kafka) for webhook workers.

## 3) Payment Correctness and Failure Modes

### (a) Concurrent `POST /invoices/:id/pay`

The service locks the invoice row with `SELECT ... FOR UPDATE`. The first request gets the lock and proceeds. The second request waits; after lock release it reads updated state and rejects invalid transition. This prevents double-charge.

### (b) PSP timeout (`tok_timeout`)

PSP call is wrapped in `tokio::time::timeout(10s)`. On timeout/network ambiguity, the attempt remains `pending`, API returns `202 Accepted`, invoice stays `open`.

### (c) PSP success then server crash before commit

Idempotency key drives retry safety. On retry with same key, existing attempt is reused rather than creating a new charge path. In production this should be combined with outbound PSP idempotency key and reconciliation.

### (d) Same idempotency key with different payload

`payment_attempts` stores `request_hash` (SHA-256 of canonical request body). Reuse with mismatch returns `409 IDEMPOTENCY_CONFLICT`.

### (e) Invoice already paid receives `/pay`

After row lock and state read, non-`open` state is rejected with `409`, and no PSP call is made.

## 4) Webhook Design

- Events: `invoice.created`, `invoice.paid`, `invoice.payment_failed`.
- Signing: HMAC-SHA256 over `{timestamp}.{payload}` with endpoint secret.
- Headers:
  - `X-Dodo-Signature: sha256=<digest>`
  - `X-Dodo-Timestamp: <unix_seconds>`
  - `X-Dodo-Event: <event_type>`
- Delivery is asynchronous via spawned task.
- Retry schedule: 1m, 5m, 30m, 2h, 8h.
- After retries exhausted: mark `dead` and keep failure context.

## 5) API Key Model

- Raw key format can be prefixed (`dp_test_` / `dp_live_`).
- Only SHA-256 hash is stored.
- Transport via `Authorization: Bearer <key>` over HTTPS.
- Rotation model: create new key, revoke old by setting `revoked_at`. and according to my decision we need to implement a cron job we checking revoked_at and and it surpass revoked at so it will generated new one and replace with old one.  
- Blast radius is isolated to a single `business_id`.

## 6) Cuts and Scope Decisions

Items intentionally not implemented:
- Refund flow and `refunds` table.
- Multi-currency support.
- Formal audit-log trail.
- Admin dashboard and webhook replay UI.
- Background reconciliation worker for pending PSP outcomes.
- Cron job is not implemented for key rotation due laks of time.

## 7) Production Readiness Gaps

- Missing metrics/tracing stack (OpenTelemetry + Prometheus).
- No per-API-key rate limiting.
- No dead-letter admin APIs for operational recovery.
